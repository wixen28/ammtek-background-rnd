# RGB Mean background extraction (with outlier rejection)

## Method

Per-pixel mean over frames sampled approximately evenly across the video,
with outlier rejection added (2026-07-23, replacing the plain mean).

The pixel-timeline diagnostic showed the pattern the rejection relies on:
a background pixel holds a stable value with small noise, and foreground
passes push it far away for a small fraction of the frames. The
per-channel **temporal median** is used purely as an internal robust
reference for that stable value (brief passes barely move it). For each
pixel, samples whose **Euclidean RGB distance** from the median exceeds
`rejection_threshold` are discarded, and the background is the **mean of
the remaining samples** — the output stays a mean; the median is not the
output. Safety fallback: if every sample of a pixel is rejected (possible
for bimodal pixels, where the median vector matches no actual sample),
the median itself is used so the algorithm cannot fail.

Because the median needs all samples at once, sampled frames are stacked
in memory (N × H × W × 3 uint8) instead of the previous running sum; the
rejection pass runs in row bands to bound float32 temporaries.

### Multi-threshold sweep (2026-07-28)

A run evaluates **several thresholds at once** and returns one background
per threshold. Picking a threshold is the main thing this experiment is
tuned on, and re-running the whole pipeline per candidate wasted most of
the work: within a row band, the float32 cast, the temporal median and
the Euclidean distance matrix do not depend on the threshold. Each band
now computes those once and repeats only the keep-mask and the masked
mean per threshold, on top of a single decode/sampling pass over the
video. The marginal cost of an extra threshold is therefore a small
fraction of a full run.

The swept backgrounds are byte-identical to running each threshold on its
own (covered by a test) — the sharing is a pure performance change.

### Shared rejection pass (2026-07-31)

The banded median / distance / keep-mask pass moved out of `rgb_mean.py`
into `processing/background/trimmed_stats.py` so Background Variation
(`2026-07-31-background-variation.md`) reuses the same implementation
instead of carrying a copy. Outputs and the API are unchanged; the existing
sweep-vs-individual-runs test is the regression guard, plus a new
band-invariance test asserting that the row-band split cannot affect
results (the median runs along the time axis, so every pixel is
independent). The band size divisor now also accounts for the
squared-distance temporary it previously ignored, so the 64 MB budget
reflects the actual working set.

## Parameters

- `use_all_frames` (default true) — process every frame of the video.
- `target_frames` — approximate number of frames used when
  `use_all_frames` is false; sampled evenly across the whole video.
- `resize` — optional output resolution used during processing.
- `rejection_thresholds` (default `[20, 30, 50]`, at most 5) — Euclidean
  RGB distances from the per-pixel temporal median beyond which a sample
  is rejected. Range 0–441.7 (√3·255); ≥442 disables rejection and
  reproduces the plain mean. One background is generated per value.

The UI presents the three defaults as editable **Low / Recommended /
High** presets. The labels live in the frontend only — the API takes and
returns plain numbers, in request order.

  sweep in the 2026-07-23 run below (33.0 % / 22.5 % / 13.3 % of samples

  reproduces the single-threshold outputs exactly.
  - **bus-stop.mp4** (1920×1080, 440 frames, all frames, no resize),
    thresholds 20/30/50: sweep **28.1 s** vs **66.5 s** for the same three
    thresholds as separate runs — **2.37× faster**. One full run is
    ~22 s, so an additional threshold costs ~3 s (roughly 7× cheaper than
    a re-run) — the decode, stack, median and distance work is shared and
    only the mask and masked mean repeat.
  - All three swept backgrounds were verified byte-identical
    (`np.array_equal`) to the same thresholds run individually, with
    matching rejected fractions (12.0 % / 9.0 % / 6.3 %) and fallback
    pixel counts (25 / 3 / 0).
  - Payload on that video: the three lossless PNG data URLs total
    **10.6 MB** in one response — acceptable over localhost, but the
    reason for the 5-threshold cap.
  - Note on timing: only one total runtime is reported for the whole
    sweep. Per-variant timings are deliberately **not** reported, because
    variants share the decode, median and distance work — a variant's
    marginal cost is not comparable to the standalone runtimes recorded
    in these notes.

- **2026-07-23 — easy_people_passing_each_other.mp4** (596×336, 219
  frames, all frames, no resize), compared against the plain mean
  (threshold 500):
  - threshold 20 → 33.0 % samples rejected; threshold 30 → 22.5 %;
    threshold 50 → 13.3 %; threshold 100 → 9.7 %. No fallback pixels at
    any of these settings. Runtime ~1.1 s (plain mean ~1.2 s — the banded
    vectorized pass costs nothing measurable on this input).
  - Degenerate check, threshold 0: 96.5 % of samples rejected and
    145 343 of 200 256 pixels (73 %) fell back to the median — the
    safety fallback works and the output is still a plausible image
    (effectively the temporal median). The remaining 27 % are pixels
    where some samples exactly equal the median vector.
  - Impact at threshold 30: large differences vs the plain mean (up to
    59/255) are concentrated in the lower image half where people pass —
    the ghosting that motivated Task 6 is removed there. In addition the
    whole image shifted slightly (median per-pixel change 13/255): the
    video contains gradual global illumination drift, which biased the
    plain mean, while the median-anchored trim recenters every pixel on
    its dominant value. The high overall rejection share (22.5 %) is
    mostly this drift, not foreground.

## Expected behavior

- Ghosting from moving objects is removed as long as the object covers a
  pixel for well under half of the sampled frames.
- Objects that sit still for about half the video or more shift the
  median itself; rejection then keeps the wrong mode and the object stays
  in the background. (The plain mean degraded more gracefully but ghosted
  everywhere.)
- The threshold trades noise robustness against sensitivity: too low
  rejects ordinary noise and lighting variation (and can push pixels to
  the median fallback), too high lets slow/large foreground back into the
  mean. Global illumination drift inflates the rejected share — the
  rejection has no temporal model, only a per-pixel distance cut.
- Memory is the main cost of the change: all sampled frames are held in
  RAM at once (e.g. ~1.9 GB for 300 Full-HD frames, ~131 MB for the
  current test video), with a transient ~2× peak while the stack is
  assembled. `resize` or `target_frames` are the mitigation.
- Response size grows linearly with the number of thresholds: every
  variant carries a full-resolution lossless PNG as a base64 data URL
  (measured 10.6 MB for three at 1920×1080). Fine over localhost, but the
  reason the list is capped at 5; `resize` is the mitigation.
- This experiment remains the baseline; RGB Median, percentile and
  trimmed-mean variants are deliberately left for later separate
  experiments.

## Diagnostics

- **Pixel timeline** (`GET /api/experiments/pixel-timeline?x=&y=`, shared
  section on every background-experiment page): plots the R/G/B values of one
  pixel across every frame of the video. Used to inspect how foreground passes
  disturb a pixel before designing outlier rejection. No sampling; purely
  observational.
  - Selection: click the generated background, click-and-drag to scrub, or
    type X/Y coordinates and press Enter —
    the marker and coordinates follow the cursor live, timeline requests are
    throttled to one per 250 ms, and the final cursor position is always
    analyzed on release. Stale responses are discarded via a request
    sequence counter.
  - **Value histogram** (2026-08-10, directly below the timeline chart, see
    `2026-08-10-pixel-value-histogram.md`): bucketed frequency distribution
    of the same samples — per-channel marginals plus the joint colour
    buckets, for judging whether the pixel has one dominant value or several
    competing modes. Computed in the browser from the timeline response; no
    extra request.
- **Background vs moving pixels** (shared section below the output, see
  `2026-07-28-movement-visualization.md`): separates one frame into static
  and moving pixels against the generated background. It always uses the
  currently selected threshold variant.
- **Threshold switcher**: buttons above the generated background select
  which variant of the completed run is shown. All variants arrive in the
  single run response, so switching is instant — no request, no
  recomputation. The metrics line and the download filename follow the
  selection. The pixel timeline always reads the original video, so
  switching backgrounds never invalidates the selected pixel or the chart.
